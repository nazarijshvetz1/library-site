# Безпечний імпорт центральних даних до D1

`scripts/import-library-core.mjs` перетворює локальний канонічний JSON-експорт Google Sheets на детермінований staging JSON. Скрипт нічого не завантажує з мережі, не відкриває Google Sheets і не записує дані до D1. Запис у робочу базу має бути окремим, контрольованим кроком після перевірки звіту.

## Дозволені джерела

Імпортер читає лише сім центральних наборів:

- `materials` / «Матеріали»;
- `covers` / «Обкладинки»;
- `locations` / «Місця»;
- `users` / «Користувачі»;
- `openingStock` / «Початкові залишки»;
- `operations` / «Операції»;
- `revisionJournal` / «Журнал ревізій».

Аркуші «Баланс», «Ревізія», тематичні каталоги, формульні зведення та інші допоміжні аркуші не імпортуються. Якщо вони є у JSON, їхні ключі потрапляють до `ignored_sheets`, а значення не впливають на результат. Поточні залишки розраховуються наново лише з початкових залишків і підтверджених операцій.

## Формат вхідного JSON

Підтримується канонічний wrapper з масивом `values`, де перший рядок — заголовки:

```json
{
  "source": {
    "spreadsheetId": "...",
    "title": "Єдина службова база підручників",
    "exportedAt": "2026-08-11T12:00:00.000Z",
    "valueRenderOption": "FORMATTED_VALUE"
  },
  "sheets": {
    "materials": {
      "sheetName": "Матеріали",
      "range": "A1:Y1381",
      "values": [["ID матеріалу", "..."], ["CAT-0001", "..."]]
    }
  }
}
```

Також кожний дозволений набір може бути масивом об’єктів або об’єктом `{ "headers": [], "rows": [] }`. Для `covers` URL читається з третьої позиції, навіть якщо заголовок третьої колонки в початковій таблиці порожній.

## Запуск dry run

Зберігайте експорт та результати в локальній приватній папці, яку не додають до Git:

```powershell
node scripts/import-library-core.mjs `
  --input .migration-private/sheets-export-2026-08-11.json `
  --output .migration-private/d1-staging.json `
  --report .migration-private/d1-reconciliation.json
```

Якщо `--output` не задано, staging bundle виводиться у stdout. За наявності помилок валідації команда повертає exit code `2`, але все одно створює результат і звіт для діагностики. URL як значення `--input` відхиляється: дозволений лише локальний файл.

## Вихідні staging-набори

- `materials` — нормалізовані картки, включно з `search_text`;
- `material_links` — посилання з колонки «Електронна версія»;
- `cover_assets` — постійні URL обкладинок;
- `locations` — фізичні й службові місця;
- `users` — користувачі та вчителі;
- `opening_stock` — початкові агреговані залишки;
- `operations` — усі операції зі збереженим статусом;
- `revision_checks` — аудит фактичних підрахунків;
- `stock_balances` — розрахований ненульовий залишок за парою CAT-ID/місце.

Це schema-neutral staging JSON. Назви й типи колонок D1 можна зіставити з остаточною схемою окремим loader-кроком, не повторюючи очищення Google Sheets.

### Статус працівника й доступ до входу

Статус «Доступ не активовано» означає лише, що працівник ще не отримав доступ до входу. Для чинних учителів, адміністрації та бібліотекарів імпортер встановлює `is_active=1`, щоб вони залишалися доступними у довіднику та для видачі матеріалів. Це не надає права входу: автентифікація й доступ до кабінету налаштовуються окремо через runtime-ідентичність та allowlist.

Статуси, які справді означають завершення роботи або неактивний запис, наприклад «Звільнений», «Колишній» чи «Неактивний», залишають `is_active=0`.

## Класифікація посилань

Посилання не перевіряються через мережу. Імпортер лише перевіряє синтаксис HTTP(S) та визначає технічний тип:

- `direct_document` — URL безпосередньо закінчується на PDF, EPUB, DOCX тощо;
- `cloud_document` — Google Drive або Google Docs;
- `commercial_page` — відомий магазин чи маркетплейс;
- `information_page` — інша HTML-сторінка.

`commercial_page` ніколи не вважається електронною книгою. Навіть `direct_document` означає лише прямий файл, а не підтверджене право доступу чи повну електронну версію. За потреби бібліотекар уточнює призначення посилання після міграції.

## Перевірки

Імпортер завершує звіт такими перевірками:

- формат та унікальність CAT-ID, LOC-ID, USR-ID й OP-ID;
- зовнішні ключі матеріалів, місць, користувачів і операцій;
- унікальність `request_id` операцій і ревізій;
- діагностика ISBN-10/ISBN-13, включно з помилками `#VALUE!` у формульній колонці;
- валідність URL без мережевих запитів;
- додатні кількості початкових залишків та операцій;
- відсутність від’ємних залишків після кожної підтвердженої операції;
- відповідність `difference = counted - expected` у журналі ревізій;
- відповідність матеріалу й кількості між ревізією та пов’язаним коригуванням;
- підсумки початкового, активного, службового та фінального фонду.

Нульовий результат ревізії також зберігається як аудит, навіть якщо він не створює операцію зміни залишку.

## Пошук

`materials.search_text` формується так само, як очікує швидкий D1 API:

1. Unicode NFKC;
2. lowercase з локаллю `uk-UA`;
3. уніфікація апострофів;
4. заміна всього, крім букв і цифр, пробілами;
5. згортання повторних пробілів.

До пошукового тексту входять CAT-ID, назва, автор, видавництво, предмет, рубрика та нормалізований ISBN. Точний CAT-ID і ISBN API має шукати окремою індексованою умовою, без `LIKE`.

## Захист персональних даних

Канонічний експорт і staging bundle можуть містити ПІБ та email. Не додавайте `.migration-private/`, результати dry run або реальний експорт до коміту, pull request чи публічного сховища. У тести дозволено додавати лише вигадані fixtures.

## Завантаження staging bundle до D1 schema 0003

`scripts/load-library-d1.mjs` виконує другий, окремий крок міграції. Він приймає лише перевірений `library-d1-staging` JSON і зіставляє його з таблицями D1 schema `0003`. Скрипт не має мережевого або production-режиму: він не викликає Cloudflare, Sites, GitHub чи Google API.

Основні правила зіставлення:

- прямий документ стає посиланням типу `ebook`;
- сторінка магазину стає `store`, а не електронною книгою;
- Google Drive/Docs стає `preview`, бо сам URL не доводить, що це повна електронна книга;
- звичайна інформаційна сторінка стає `details`;
- обкладинки з чинними URL переносяться як зовнішні assets; самі байти цим loader не завантажуються;
- активні фізичні місця утворюють `holdings`; службові місця на кшталт «Списано» і «Втрачено» не рахуються як доступний фонд;
- початкові залишки та підтверджені операції відтворюються у `inventory_transactions` і `inventory_transaction_lines`;
- старі видачі без позичальника і `loan_id` не перетворюються на вигадані позики: вони зберігаються як рух між місцями;
- непідтверджені операції не змінюють фонд, але зберігаються в `audit_events`;
- журнал ревізій зберігається в `audit_events`, пов'язаних із відповідними транзакціями;
- `material_stock_totals` заново обчислюється з цільових `holdings`.

### Безпечний dry-run

Без параметра `--apply-local` команда нічого не записує. Якщо `--database` не задано, вона лише будує й перевіряє детермінований план:

```powershell
node scripts/load-library-d1.mjs `
  --input .migration-private/d1-staging.json `
  --plan .migration-private/d1-hosted-load-plan.json `
  --report .migration-private/d1-load-plan-report.json
```

`--plan` створює саме той файл, який приймає `/librarian/import`: компактний
стабільно впорядкований UTF-8 JSON з одним завершальним `LF`. У
`hosted_plan.sha256` та `hosted_plan.byte_length` звіту записуються hash і
розмір точних байтів цього файла. Саме цей SHA-256 треба тимчасово задати як
`LIBRARY_IMPORT_PLAN_SHA256`; pretty-print або повторне збереження редактором
змінить hash. План містить службові та персональні дані й має залишатися лише
у `.migration-private/`.

Для reconciliation із уже підготовленою локальною копією SQLite/D1 schema `0003`:

```powershell
node scripts/load-library-d1.mjs `
  --input .migration-private/d1-staging.json `
  --database .migration-private/library-local.sqlite `
  --report .migration-private/d1-dry-run.json
```

У звіті для кожної цільової таблиці є кількість `new`, `unchanged`, `conflicts` і `extra_existing`. Будь-яка відмінність рядка з уже наявним первинним ключем або зіткнення іншого унікального ключа зупиняє loader до запису. Наявні дані не перезаписуються.

### Явний запис лише до локальної копії

Запис дозволяється тільки явним параметром `--apply-local` і тільки до наявного локального SQLite-файлу:

```powershell
node scripts/load-library-d1.mjs `
  --input .migration-private/d1-staging.json `
  --database .migration-private/library-local.sqlite `
  --apply-local `
  --report .migration-private/d1-local-apply.json
```

Усі нові рядки виконуються одним SQLite/D1 batch. Якщо хоча б один statement не проходить constraint або trigger, весь batch відкочується. Loader не ділить невдалий запис на частково успішні пакети. Повторний запуск спочатку порівнює всі цільові рядки: ідентичні рядки позначаються `unchanged`, нових записів не створюється.

Production D1 не слід підключати до CLI. Для майбутнього контрольованого перенесення функції `buildD1LoadPlan()`, `inspectD1LoadPlan()` і `loadD1Plan()` можна викликати з одноразового адміністративного середовища, передавши справжній D1 binding. Це має бути окремий погоджений крок після перевірки dry-run і резервної копії.

## Одноразовий hosted-import лише для staging

Маршрут `/librarian/import` призначений лише для контрольованого завантаження
вже побудованого `library-d1-load-plan` JSON до окремої порожньої staging D1.
Він не приймає staging bundle, SQL, URL або архів. Production-конфігурація не
повинна містити ввімкнений import-прапорець.

Перед коротким вікном імпорту в приватному staging deployment задаються:

- `APP_ENV=staging`;
- `LIBRARY_IMPORT_ENABLED=true`;
- `LIBRARY_IMPORT_ALLOWED_ORIGIN` — точний HTTPS origin staging-сайту без шляху;
- `LIBRARY_IMPORT_PLAN_SHA256` — SHA-256 точних байтів перевіреного JSON-плану;
- `LIBRARY_IMPORT_EXPIRES_AT` — ISO-8601 час у майбутньому, не далі ніж через 7 діб;
- звичайний `LIBRARIAN_ALLOWED_EMAILS` для ChatGPT-auth allowlist;
- `LIBRARIAN_WRITES_ENABLED=false` залишається незалежно вимкненим.

До першого upload у staging для R2 bucket `COVER_UPLOADS` обов’язково налаштовують
і перевіряють lifecycle rule **лише** для префікса `_migration/library-d1/`:
видалення об’єктів через **45 діб**. Коротший строк не підходить, бо сесія може
мати до 7 діб активного вікна і ще до 30 діб recovery grace для verify/cleanup.
Правило є страховкою для унікального orphan-об’єкта, якщо після R2 PUT результат
D1-запису та повторного читання лишився невизначеним. Воно не повинно охоплювати
обкладинки або інші ключі bucket. Наявність правила треба підтвердити в hosting/R2
до ввімкнення `LIBRARY_IMPORT_ENABLED`; сам код сайту не створює lifecycle policy.

Послідовність у прихованій консолі фіксована:

1. **Upload** перевіряє розмір до 6 МіБ, строгий контракт, SHA-256 і кладе
   файл лише у приватний R2-префікс `_migration/library-d1/`.
2. **Preflight** лише читає D1. Він відмовляється працювати, якщо цільові
   таблиці не порожні, є конфлікти, зайві чи вже наявні рядки.
3. **Atomic commit** повторно читає hash-pinned план з R2, сам будує
   детерміновані INSERT statements і виконує їх, FTS rebuild та зміну
   службового статусу одним D1 batch. Клієнт ніколи не надсилає SQL.
4. **Verify** незалежно звіряє всі рядки, конфлікти й зайві дані, виконує
   FTS5 external-content `integrity-check` з `rank=1` та детерміновані
   `MATCH` smoke tests. Сам `COUNT(*)` не вважається доказом справного індексу.
5. **Cleanup** після успішного verify видаляє приватний JSON із R2, але
   залишає компактний журнал `migration_import_runs` у D1. Прострочену
   сесію, яка зупинилася на upload/preflight і ще не писала фонд, можна
   безпечно abort/cleanup у межах 30-добового службового grace period.

Кожна фаза дозволена лише власнику сесії та лише з точного staging origin.
Повтор того самого запиту є resumable/idempotent: він повертає вже збережений
статус, але не виконує import вдруге. Після cleanup треба негайно встановити
`LIBRARY_IMPORT_ENABLED=false` і прибрати hash/expiry з environment. Сам факт
успішного staging-import не є дозволом на production cutover.
