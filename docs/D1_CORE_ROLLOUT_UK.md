# Контрольований rollout D1 Phase 1

## 1. Призначення документа

Цей документ описує перехід сайту бібліотеки на Cloudflare D1 як операційне ядро. Він не є дозволом на production-запис і не стверджує, що cutover уже виконано.

Поточний безпечний стан:

- код D1 Phase 1 підготовлено й перевіряється локально;
- production Sites `LIBRARIAN_WRITES_ENABLED=false`;
- legacy Apps Script `LIBRARIAN_WRITES_ENABLED=false`;
- Google Sheets залишається чинним джерелом експорту, звіряння та архівною копією;
- production rollout заборонений до staging-імпорту реальних даних і повного E2E.

Підготовка експорту, dry-run, reconciliation і локального loader описані окремо: [D1_IMPORTER_UK.md](D1_IMPORTER_UK.md).

## 2. Цільова модель Phase 1

Після підтвердженого cutover сайт читає й змінює щоденні бібліотечні дані в D1.

| Контур | Призначення після cutover |
| --- | --- |
| D1 `DB` | матеріали, посилання, місця, залишки, рух, користувачі, видачі, повернення, аудит та ідемпотентність |
| R2 `COVER_UPLOADS` | резерв для приватного cover workflow; прямий новий D1-upload ще не входить до Phase 1 |
| Google Sheets | архів/лише читання, джерело міграції та аварійного порівняння |
| Apps Script | legacy-контур, вимкнений для production-запису |
| Sites | захищений інтерфейс, runtime bindings, доступ і серверний прапорець запису |

Не допускається постійний dual-write, коли одна операція паралельно вважається головною і в D1, і в Google Sheets.

## 3. Операційні сценарії D1

Новий кабінет не створює проміжну службову чернетку для основних щоденних дій.

| Сценарій | API | Запобіжник |
| --- | --- | --- |
| Пошук і фільтри | `GET /api/librarian/materials/search` | автентифікація, bounded limit, cursor |
| Детальна картка | `GET /api/librarian/materials/:id` | роль бібліотекаря; службові поля не потрапляють у public API |
| Новий матеріал | `POST /api/librarian/materials` | автоматичний CAT-ID, `requestId`, одна атомарна команда |
| Редагування матеріалу й посилань | `PATCH /api/librarian/materials/:id` | `expectedVersion`, конфлікт замість перезапису |
| Надходження | `POST /api/librarian/receipts` | очікуваний залишок, транзакція й аудит |
| Фактична кількість | `POST /api/librarian/stock-adjustments` | очікуваний залишок, причина й дата |
| Видача вчителю | `POST /api/librarian/loans` | активний учитель, доступний залишок, `requestId` |
| Перелік відкритих видач | `GET /api/librarian/loans` | автентифікований read, фільтр учителя |
| Повернення | `POST /api/librarian/loans/returns` | контроль неповерненої кількості й атомарний рух |

Окремий щоденний пункт «Ревізія» у новому flow не потрібен. Його практичну дію виконує «Встановити фактичну кількість», а кожний підрахунок зберігається в журналі транзакцій та аудиті.

Legacy draft routes, Sheets gateway і старий інтерфейс не видаляються під час Phase 1. Вони залишаються резервним контуром і джерелом історичного контексту, але не є основним workflow після cutover.

## 4. Межа Phase 1 для обкладинок

Міграція переносить метадані й чинні постійні URL обкладинок. Каталог і кабінет продовжують показувати ці зображення.

Не входить до Phase 1:

- пряме завантаження нової фотографії з D1-форми;
- новий пошук обкладинки за ISBN у прямому D1 flow;
- перенесення самих байтів усіх чинних зображень loader-ом;
- автоматична заміна наявного JPG.

До окремого cover-етапу старий перевірений workflow не видаляється. Створення матеріалу без фото є допустимим, але інтерфейс має чітко показувати, що обкладинка ще не додана.

## 5. Обов’язкові умови до staging

Перед першим staging-імпортом потрібно:

1. Зафіксувати конкретну версію коду, D1 schema й міграцій.
2. Виконати локальні `npm run build` і повний тестовий набір.
3. Створити датовану копію Google Sheets.
4. Зробити канонічний локальний експорт усіх центральних наборів.
5. Зберігати експорт лише у `.migration-private/` або іншому приватному сховищі.
6. Побудувати staging bundle і reconciliation-звіт.
7. Усунути всі помилки CAT-ID, LOC-ID, USR-ID, ISBN, зовнішніх ключів і балансів.
8. Перевірити, що жоден реальний email, експорт або секрет не потрапив до Git.

Формульні аркуші та тематичні каталоги не повинні ставати окремими D1-джерелами істини.

## 6. Локальний dry-run і reconciliation

Послідовність команд та формати звітів наведено в [D1_IMPORTER_UK.md](D1_IMPORTER_UK.md). Мінімальний результат, який дозволяє перейти далі:

- імпортер завершується без validation errors;
- кількість матеріалів і унікальних CAT-ID збігається з канонічним експортом;
- усі посилання прив’язані до наявних матеріалів;
- усі holdings посилаються на активні матеріали й місця;
- `material_stock_totals` відтворено з holdings та відкритих видач;
- `conflicts=0` у loader report;
- повторний локальний apply дає лише `unchanged`, а не нові дублікати;
- непідтверджені старі операції не змінюють поточний фонд.

Production D1 не підключається до локального CLI. Майбутній production import виконується окремим одноразовим контрольованим процесом зі справжнім D1 binding після письмового погодження результату staging.

## 7. Staging-середовище

Staging має бути відокремлене від production:

- окрема D1 база;
- окремий Sites deployment або чітко відокремлений environment;
- окремий список тестових дозволених облікових записів;
- жодного production токена чи production D1 binding;
- staging URL не індексується пошуковими системами.

Рекомендована послідовність:

1. Розгорнути schema й міграції в порожній staging D1.
2. Завантажити перевірений staging bundle контрольованим loader-процесом.
3. Повторити reconciliation вже проти staging D1.
4. Розгорнути Sites із `LIBRARIAN_WRITES_ENABLED=false`.
5. Перевірити автентифікацію, read API, пошук, картки, роки, фото, посилання й залишки.
6. Лише у staging тимчасово встановити `LIBRARIAN_WRITES_ENABLED=true` для E2E.
7. Після тесту знову встановити staging-прапорець у `false`, доки не буде підписаний протокол результатів.

Production-прапорці протягом усього staging залишаються `false`.

## 8. Обов’язковий E2E-чекліст

### Доступ і витік даних

- неавторизований користувач не відкриває кабінет та службові API;
- користувач без ролі бібліотекаря отримує відмову;
- public API не повертає приватні notes, непублічні links, service locations або дані вчителів;
- cross-origin POST відхиляється;
- при `LIBRARIAN_WRITES_ENABLED=false` усі POST/PATCH fail closed.

### Читання й швидкість

- пошук знаходить матеріал за назвою, автором, ISBN і CAT-ID;
- фільтри рубрики, класу, предмета, типу й наявності працюють окремо та разом;
- cursor не повторює й не пропускає записи;
- у результатах є рік та thumbnail;
- детальна картка підвантажує links і holdings лише після відкриття;
- чинні обкладинки відображаються, а відсутня обкладинка не ламає картку.

### Прямі операції

- новий матеріал отримує наступний унікальний CAT-ID;
- новий матеріал може атомарно створитися з початковим надходженням;
- пряме редагування змінює лише дозволені поля й посилання;
- застаріла `expectedVersion` повертає конфлікт без часткового запису;
- надходження збільшує потрібний holding і stock totals;
- фактичний підрахунок зменшує, збільшує або підтверджує залишок;
- видача вибраному за прізвищем учителю зменшує доступну кількість;
- часткове повернення залишає видачу відкритою;
- повне повернення закриває видачу;
- повернення до іншого дозволеного місця правильно змінює holdings;
- однаковий `requestId` не створює дубль;
- одночасна зміна залишку повертає конфлікт, а не від’ємну кількість.

### Звіряння після E2E

- `total_quantity = library_quantity + other_location_quantity + loaned_quantity`;
- `available_quantity = total_quantity - loaned_quantity`;
- ненульові holdings відповідають деталям картки;
- кожна write-операція має command, transaction/audit event і завершений результат;
- після E2E staging можна повернути до початкового snapshot або повністю пересоздати.

## 9. Умови дозволу на production cutover

Cutover дозволяється лише коли одночасно виконано все:

- staging import завершився без невирішених конфліктів;
- E2E-чекліст підписано;
- резервну копію Sheets відкрито й перевірено;
- створено й перевірено backup/snapshot production D1;
- є точний план відкату та відповідальна особа;
- визначено коротке вікно замороження змін у Google Sheets;
- відсутні критичні або високі дефекти;
- бібліотекар підтвердив вибірку матеріалів, посилань, обкладинок і залишків;
- production runtime secrets/bindings перевірені без показу значень у логах;
- окремо погоджено момент зміни Sites `LIBRARIAN_WRITES_ENABLED` з `false` на `true`.

Сам факт успішної збірки, green unit tests або наявності D1 routes не є дозволом на cutover.

## 10. Production cutover

1. Встановити погоджене вікно й припинити службові зміни в Google Sheets.
2. Зробити фінальний експорт і датовану резервну копію.
3. Повторити importer/reconciliation на фінальному експорті.
4. Завантажити дані до production D1 одноразовим контрольованим процесом.
5. Звірити row counts, CAT-ID, links, users, locations, holdings і totals.
6. Розгорнути Sites із production bindings, але `LIBRARIAN_WRITES_ENABLED=false`.
7. Виконати read-only smoke test публічного каталогу й кабінету.
8. Виконати один погоджений canary після окремого ввімкнення Sites write flag.
9. Перевірити canary у UI, D1 transaction/audit і stock totals.
10. Лише після успішної перевірки залишити D1-запис увімкненим.
11. Legacy Apps Script write flag залишити `false`.
12. Перевести Google Sheets у режим архіву/лише читання та зафіксувати час cutover.

Не слід відновлювати паралельне ручне ведення фонду в Sheets після кроку 12.

## 11. Відкат

При критичній помилці:

1. Негайно встановити Sites `LIBRARIAN_WRITES_ENABLED=false`.
2. Зафіксувати час, останній успішний `requestId` і перелік операцій після cutover.
3. Не повторювати запити з новими `requestId`, якщо результат невідомий.
4. Повернути попередній deployment Sites або від’єднати проблемний D1 binding.
5. Не змішувати частково відновлені D1-дані з новими ручними записами Sheets.
6. Порівняти audit/transactions із журналом фактичних дій бібліотекаря.
7. Відновити D1 зі snapshot або створити нову базу з останнього перевіреного експорту.
8. Лише після reconciliation прийняти окреме рішення: повторити cutover або тимчасово повернути legacy-контур.

Архівна Google Sheets потрібна для відновлення й порівняння, але вона не повинна мовчки отримати статус актуальної бази без формального рішення та перенесення всіх операцій після cutover.

## 12. Що має бути наступним після Phase 1

- пряме безпечне додавання обкладинки з фото/ISBN/URL;
- перенесення решти адміністративних сценаріїв навчальних років і класів;
- перевірена стратегія резервного копіювання D1/R2;
- спостереження за latency/error rate й алерти;
- остаточне видалення legacy draft/Sheets коду лише після стабільного production-періоду та окремого погодження.
