# Графік відвідування бібліотеки

Гостьова власність, редагування візитів у кабінеті, самостійна зміна коду та rollout міграції `0009` описані в [TEACHER_PORTAL_UK.md](./TEACHER_PORTAL_UK.md).

Графік працює без Google Sheets. Розклад, записи та захист від накладок зберігаються безпосередньо в D1.

## Що бачать відвідувачі

У публічному каталозі є розділ **«Графік відвідування бібліотеки»**. Він показує лише:

- години роботи бібліотеки;
- вільні проміжки;
- зайняті проміжки;
- періоди, коли бібліотека зачинена.

Публічна відповідь API навмисно не містить прізвищ, email, класів, мети візиту, внутрішніх ID записів або службових приміток. Вже зайнятий час позначається просто як **«Заброньовано»**.

## Як учитель записується

1. У публічному графіку вчитель обирає вільний проміжок і переходить на `/visits`; до URL передаються лише дата та час.
2. Учитель вводить щонайменше три літери свого імені, обирає себе з активного довідника D1 та вводить виданий бібліотекарем особистий код формату `XXXXX-XXXXX`. Email і вхід через ChatGPT для вчителя не потрібні.
3. Сервер використовує канонічне `users.full_name`; учитель не вводить і не може підмінити своє прізвище. За бажанням він обирає активний клас і додає коротку мету.
4. Після надсилання час бронюється одразу. Якщо інший користувач зайняв хоча б частину проміжку раніше, сервер повертає конфлікт без часткового запису.
5. Учитель бачить лише власні майбутні записи й може їх скасувати.

Повне ім’я та клас зберігаються як приватні дані. Їх бачать лише власник запису та авторизований бібліотекар. Публічний графік персональні дані не розкриває.

Після успішного входу сервер встановлює випадкову `__Host-visit_teacher` cookie на 12 годин (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`). У D1 зберігається лише SHA-256 від токена, а не сама cookie. Одночасно підтримуються три активні сеанси; четвертий успішний вхід відкликає найстаріший. Блокування через невдалі спроби забороняє лише новий вхід і не перериває вже підтверджений сеанс.

## Правила часу

- часовий пояс: `Europe/Kyiv`;
- точність сітки: 5 хвилин;
- тривалість одного відвідування: від 20 до 240 хвилин;
- дата: від поточного дня до 90 днів наперед;
- початок і завершення мають належати до відкритих годин;
- закриття бібліотеки та чинний запис блокують відповідні п’ятихвилинні сегменти.

У першій версії для кожного дня тижня налаштовується один безперервний інтервал роботи. API все одно повертає масив інтервалів, щоб надалі можна було додати, наприклад, окремі ранкові та післяобідні години без зміни публічного контракту.

Накладки забороняються в самій D1-транзакції унікальними сегментами часу. Перевірка в браузері потрібна лише для зручності й не є єдиним захистом.

## Кабінет бібліотекаря

Сторінка `/librarian/visits` доступна лише користувачам із чинним бібліотекарським доступом. Вона показує приватний розклад із прізвищем, класом і метою та дозволяє скасувати активний запис. Усі операції мають `requestId`, перевірку версії та безпечний повтор після втраченої відповіді.

Скасований запис не видаляється: зберігаються його стан, версія, час скасування та ідентифікатор відповідальної сторони. Публічний API цих даних не повертає. Адміністративні дії бібліотекаря додатково потрапляють до службового аудиту.

У керуванні доступом бібліотекар може видати або перевидати код одному активному вчителю, вимкнути/увімкнути доступ, розблокувати його чи відкликати всі сеанси. Масова видача створює коди лише активним учителям без credential і ніколи мовчки не обертає наявні коди. Код повертається відкритим текстом лише в одній `private, no-store` відповіді; у credential, audit та idempotency-команді зберігаються тільки HMAC/безпечні метадані. Повтор того самого `requestId` не показує код повторно, а повертає `code_result_unrecoverable`.

CSV/друк із кодами існує лише в браузері. Його треба одразу безпечно передати вчителям, не надсилати у спільні чати, не зберігати в репозиторії та видалити після роздачі. Втрачений код не відновлюється — бібліотекар явно створює новий, що відкликає старі сеанси.

Прізвище, email, клас, мета візиту та завершені idempotency-команди є приватними службовими даними. Перед production слід затвердити строк їх зберігання; рекомендовано регулярно очищати завершені команди після завершення безпечного вікна повтору, а персональні поля скасованих або минулих записів анонімізувати згідно з політикою ліцею, не змінюючи агрегований публічний розклад і незамінний адміністративний аудит.

## Runtime-прапорці

- `VISIT_SCHEDULE_ENABLED=true` вмикає читання графіка;
- `VISIT_BOOKING_ENABLED=true` вмикає створення і скасування записів;
- `VISIT_TEACHER_CODE_AUTH_ENABLED=true` окремо вмикає довідник, вхід за особистим кодом і teacher-session API; значення за замовчуванням — `false`;
- `VISIT_TEACHER_AUTH_PEPPER` — стабільний випадковий production-secret щонайменше з 32 символів/байтів. Його треба резервно зберігати у менеджері секретів; зміна pepper робить усі раніше видані коди непридатними;
- `LIBRARIAN_WRITES_ENABLED=true` окремо керує адміністративними діями бібліотекаря.

Login-rate limits рахують лише невдалі спроби: 5 за 15 хвилин для пари IP+teacher, coarse-поріг 300 за 15 хвилин для спільного шкільного NAT та 20 за 60 хвилин для credential; лише останній поріг тимчасово блокує новий вхід учителя. Пошук у довіднику має окремий coarse-ліміт 300 запитів за хвилину на IP; результат усе одно обмежений десятьма активними вчителями. Якщо платформа не передала довірений `CF-Connecting-IP`, довідник і вхід fail closed з 503, не створюючи спільний bucket `unknown`.

## Основні API

- `GET /api/visits/public?from=YYYY-MM-DD&to=YYYY-MM-DD` — публічний графік без персональних даних;
- `GET /api/visits/teacher/directory?q=...` — до 10 активних учителів як `{loginId, fullName, publicHint}` без внутрішнього `users.id`;
- `POST /api/visits/teacher/session` з точним `{loginId, code}` — створення teacher cookie;
- `GET /api/visits/teacher/session` — `{teacher:{fullName}, pendingScope, expiresAt}` або 401;
- `DELETE /api/visits/teacher/session` — вихід і відкликання поточної cookie;
- `GET /api/visits/teacher?from=YYYY-MM-DD&to=YYYY-MM-DD` — власні записи та доступні класи;
- `POST /api/visits/teacher` — атомарне бронювання;
- `DELETE /api/visits/teacher/:id` — скасування власного запису;
- `GET /api/librarian/visits` — приватний розклад;
- `DELETE /api/librarian/visits/:id` — адміністративне скасування.
- `GET /api/librarian/visits/teacher-access` — список активних учителів і станів доступу;
- `POST /api/librarian/visits/teacher-access/:teacherId/code` — одноразова видача/заміна коду;
- `PATCH /api/librarian/visits/teacher-access/:teacherId` — `enable`, `disable`, `unlock` або `revoke_sessions`;
- `POST /api/librarian/visits/teacher-access/bulk-issue` — атомарна видача відсутніх кодів із підтвердженням `ISSUE_MISSING_ONLY`.

Публічний API може дозволяти CORS для читання з GitHub Pages. Усі операції запису виконуються лише на Sites після автентифікації та same-origin перевірки.

## Перевірка перед production

1. Застосувати `0008_sudden_thunderbird.sql` у staging з `VISIT_TEACHER_CODE_AUTH_ENABLED=false` і `VISIT_BOOKING_ENABLED=false`; перевірити `PRAGMA foreign_key_check`, кількість бронювань/slot claims та канонічний backfill власників.
2. Створити стабільний випадковий `VISIT_TEACHER_AUTH_PEPPER` (мінімум 32), зберегти його резервну копію в менеджері секретів і не логувати значення.
3. Залишаючи teacher code-auth вимкненим, увімкнути бібліотекарські записи, видати коди, безпечно роздати їх і перевірити, що plaintext не потрапив у D1/audit/logs.
4. Увімкнути `VISIT_SCHEDULE_ENABLED` у staging й перевірити публічне читання графіка та відсутність PII; `VISIT_BOOKING_ENABLED` поки залишити вимкненим.
5. Увімкнути `VISIT_TEACHER_CODE_AUTH_ENABLED`, перевірити пошук, formatted-code login, cookie, вихід, wrong-code limits, reset/revoke та три активні сеанси. Потім увімкнути `VISIT_BOOKING_ENABLED`, створити/скасувати запис, перевірити конфлікт двох одночасних запитів та replay `requestId`.
6. Лише після E2E повторити порядок у production: міграція → pepper → видача кодів → FK/backfill/session checks → code-auth → booking.

Staging import/reset видаляє teacher credentials, sessions, login limits і access commands. Після такого reset коди треба видати повторно до повторного ввімкнення `VISIT_TEACHER_CODE_AUTH_ENABLED`; інакше вчителі не зможуть увійти.
