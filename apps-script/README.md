# Apps Script для сайту бібліотеки

Ця папка містить повний контрольований snapshot продуктивного Apps Script і два канали роботи з тією самою службовою Google-таблицею:

- `PublicCatalogApi.gs` — публічний `doGet` з безпечним набором даних для каталогу вчителів;
- `LibrarianGateway.gs` — захищений `doPost`, HMAC, цільове середовище й оркестрація застосування;
- `LibrarianApplyJournal.gs` — довговічний ідемпотентний журнал і контрольні точки відновлення;
- `LibrarianApplyOperations.gs` — явні обробники всіх одинадцяти службових операцій і безпечні структурні ремонти;
- `LibrarianCoverBridge.gs` — запис кінцевої обкладинки або асинхронне опрацювання URL;
- `Код.gs` і `CoverAutomation.gs` — чинні формули/фільтри та попередня автоматизація обкладинок, які потрібно зберігати під час `clasp push`.

Публічний канал є лише читанням. Продуктивне розгортання Apps Script v6 містить захищений шлюз і точний OAuth scope `spreadsheets`. Запис неможливий, доки `LIBRARIAN_WRITES_ENABLED=false` хоча б в одному з двох місць: у Sites або Script Properties. Після контрольного продуктивного тесту обидва прапорці повернуто в `false`.

## Що повертає публічний API

Публічний канал повертає бібліографічні дані, обкладинки та доступні залишки. Він не повинен повертати електронні адреси, внутрішні примітки, журнал операцій або службові записи, не потрібні вчителям.

## Що повертає захищений шлюз

Після перевірки HMAC-підпису шлюз повертає:

- учителів, адміністрацію та бібліотекаря без електронних адрес;
- звичайні місця зберігання без службових місць списання/втрат;
- навчальні роки;
- класи в розрізі навчальних років із керівником, кабінетом, датами та станом.

Запит має короткий термін дії, одноразовий nonce і підпис. Повторний або прострочений запит відхиляється.

Дія `applyDraft` має явний обробник для кожного типу: матеріал (створення/редагування), надходження, переміщення, списання, ревізія, навчальний рік, клас (створення/редагування/закриття) і групове переведення. Вона перевіряє ID таблиці, режим цілі, структуру й формули аркушів, HMAC, `requestId`, відповідального користувача, контрольну версію матеріалу/класу, перевірений залишок та обидва прапорці запису.

Перед першою доменною зміною створюється прихований аркуш `Журнал застосувань`. У ньому зберігаються fingerprint, план, цільові рядки, контрольні точки та результат. Повтор того самого `requestId` звіряє вже виконані кроки й не створює дубль. Якщо відповідь втрачена після часткового запису, журнал лишається у стані `applying`, а повтор продовжує той самий план. Помилка актуальності до першого запису повертає чернетку до редагування.

## Script Property

У налаштуваннях Apps Script потрібно створити Script Property:

```text
SHEETS_GATEWAY_SECRET
SPREADSHEET_ID
PUBLIC_CATALOG_SPREADSHEET_ID
LIBRARIAN_WRITE_MODE=copy_test
LIBRARIAN_WRITES_ENABLED=false
GITHUB_OWNER=nazarijshvetz1
GITHUB_REPO=library-covers
GITHUB_TOKEN
```

Значення має бути випадковим секретом щонайменше з 32 символів. Той самий секрет потрібно зберегти в runtime-змінній Sites `SHEETS_GATEWAY_SECRET`.

`GITHUB_TOKEN` потрібен лише для остаточного запису обкладинки та запуску URL-workflow. Використовуйте окремий fine-grained token з мінімальними правами до `library-covers`; не використовуйте пароль, токен з іншого облікового запису або широкі права організації. Після підозри на витік токен потрібно спочатку замінити у Script Properties, перевірити одну обкладинку, а потім відкликати старий.

`SPREADSHEET_ID` є обов’язковим: код більше не має резервного переходу на продуктивну таблицю. Для тесту повної копії використовуйте `LIBRARIAN_WRITE_MODE=copy_test`; цей режим прямо відхиляє ID продуктивної таблиці. Значення `production` дозволяється лише разом із точним ID основної службової таблиці та не означає, що запис уже ввімкнено.

`PUBLIC_CATALOG_SPREADSHEET_ID` керує тільки публічним каналом читання й не успадковує `SPREADSHEET_ID` шлюзу запису. У staging задайте йому ID повної копії. Якщо властивість відсутня, для сумісності з чинним v6 використовується лише відомий продуктивний ID; явно порожнє або некоректне значення завершується помилкою, а не переходом на іншу таблицю.

Авторизаційним джерелом для входу є `LIBRARIAN_ALLOWED_EMAILS` у Sites. Apps Script незалежно перевіряє, що той самий email рівно один раз присутній серед активних записів аркуша `Користувачі`. Перейменування ролі в таблиці саме по собі не відкликає право запису: для негайного відкликання приберіть email зі списку дозволених у Sites та/або позначте користувача неактивним.

Не вставляйте значення секрету:

- у вихідний код;
- у клітинки Google Sheets;
- у документацію;
- у Git-репозиторій;
- у скриншоти або повідомлення.

## Підключення

1. Відкрийте службову Google-таблицю.
2. Оберіть **Розширення → Apps Script**.
3. Перед push зробіть read-only snapshot віддаленого проєкту й переконайтеся, що набір файлів відповідає цій папці.
4. Передайте повний вміст `apps-script/`; не робіть частковий `clasp push`, який може видалити `Код.gs` або `CoverAutomation.gs`.
5. У **Налаштуваннях проєкту → Властивості скрипту** додайте `SHEETS_GATEWAY_SECRET`, точні `SPREADSHEET_ID` і `PUBLIC_CATALOG_SPREADSHEET_ID`, `LIBRARIAN_WRITE_MODE` та `LIBRARIAN_WRITES_ENABLED=false`.
6. Спочатку розгорніть окремий staging-проєкт для повної копії таблиці, з іншим секретом, режимом `copy_test` і вимкненим записом.
7. Виконайте `setupLibrarianGatewayDataRepairs()` на копії та звірте його звіт. Функція не змінює бібліографічні чи облікові значення: вона ідемпотентно розширює перевірені формули/валідації або відмовляється, якщо структура невідома. Для нових операцій вона працює лише з generic-діапазоном `Операції!2:1000`, додає й приховує `Операції!P` як службовий `requestId`-маркер для ідемпотентного відновлення після сортування та не торкається legacy-моста ревізії в рядках `1201+`.
8. Перевірте всі одинадцять сценаріїв, повтор того самого `requestId`, застарілі знімки та відновлення після змодельованого збою. Після тесту поверніть обидва прапорці у `false`.
9. Перед production-оновленням створіть нову копію таблиці та перевірте маніфест. Він має містити `spreadsheets`, `script.external_request` і `script.scriptapp`, але не Drive scope. Нові зовнішні scope потребують повторної авторизації.
10. У production створіть нову immutable-версію й оновіть чинне web-app deployment, щоб URL `/exec` не змінився.
11. У Sites задайте той самий секрет як `SHEETS_GATEWAY_SECRET`; у Sites та Script Properties залиште `LIBRARIAN_WRITES_ENABLED=false`, доки контрольний canary не підтвердить нову версію.

Якщо в історії розгортань уже є версія з іншим номером, не намагайтеся штучно змінити нумерацію. Створіть наступну версію та зафіксуйте фактичний номер у службовому журналі.

Прив’язаний продуктивний Apps Script має чинні тригери `onEditCoverAutomation`, `onOpenCoverAutomation` і `checkPendingCoverRequests`. Повний snapshot тепер входить до цієї папки, однак перед кожним production push усе одно потрібно порівнювати його з віддаленим проєктом і не змінювати/видаляти невідомі файли або тригери.

## Перевірка після розгортання

Перевіряйте через захищений кабінет, а не вставляючи секрет у URL:

1. Публічний каталог відкривається і завантажує матеріали.
2. Захищений кабінет доступний тільки дозволеному користувачу.
3. Запит довідників повертає вчителів, місця, навчальні роки та класи.
4. У відповіді немає електронних адрес.
5. Службові місця списання/втрат не з’являються серед кабінетів.
6. Запит без підпису, зі старим часом або повторним nonce відхиляється.
7. Після read-only тесту Google Sheets не має жодних змін від шлюзу.
8. На повній копії в режимі `copy_test` перевірте всі одинадцять типів, а не лише навчальний рік.
9. Для кожного типу виконайте успішний запис, повтор того самого `requestId`, неактуальний snapshot і контроль формул/залишків. Для багатокрокової операції змоделюйте збій після першого запису й підтвердьте бездубльове продовження.
10. Окремо перевірте приватне фото, URL обкладинки, відсутність проміжного фото в GitHub, остаточний URL у `Матеріали`/`Обкладинки` та видалення R2 лише після підтвердженого постійного запису.
11. Для продуктивного canary спочатку застосуйте один точний no-op, потім одну малоризикову реальну операцію; після перевірки одразу поверніть обидва прапорці в `false` і порівняйте контрольні діапазони з резервним знімком.

## Безпека

- Вебзастосунок виконується від імені власника таблиці. Підготовлений запис потребує scope `spreadsheets`, тому головними запобіжниками є серверна перевірка виду операції, HMAC, обов’язковий ID таблиці, точний режим цілі та два незалежні прапорці запису.
- Відкритий URL `/exec` не є секретом; захист службового `doPost` забезпечує HMAC-підпис.
- Apps Script не повинен логувати тіло підписаного запиту, секрет або значення інших Script Properties.
- Не додавайте до відповіді аркуш користувачів повністю чи приватні контакти.
- Зміна коду Apps Script не оновлює чинне розгортання автоматично — щоразу створюйте нову версію.
- `LIBRARIAN_WRITES_ENABLED=false` залишається вимкненим у Sites і Apps Script. Не вмикайте обидва прапорці до тесту на копії та окремого рішення бібліотекаря.

## Відновлення

Якщо після оновлення шлюз не працює:

1. Не вмикайте запис до Sheets.
2. У керуванні розгортаннями поверніть вебзастосунок на попередню перевірену версію.
3. Перевірте, що URL `/exec` не змінився.
4. Звірте наявність `SHEETS_GATEWAY_SECRET` у Apps Script і Sites, не розкриваючи значення.
5. За підозри на витік згенеруйте новий секрет і замініть його з обох боків.
6. Повторіть перевірки публічного каталогу й захищених довідників.
7. Якщо відповідь на майбутній запит запису була втрачена, повторіть його з тим самим `requestId`; не створюйте новий ідентифікатор.

Стара інструкція для публічного каталогу збережена у `README_UK.md`; цей файл є актуальним описом двох каналів і захищеного шлюзу.
