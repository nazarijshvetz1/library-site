# Сайт бібліотеки Міжнародного ліцею МАУП

Проєкт працює в наявному Sites-проєкті з тим самим D1 і R2 та має чітко розділені контури:

- власний каталог підручників, робочих зошитів та інших навчальних матеріалів;
- захищений кабінет бібліотекаря для внутрішніх облікових операцій;
- кабінети вчителя й учня, Telegram-сервіси та голосові помічники;
- прямі переходи до Librarika для художньої й наукової літератури.

Librarika є єдиною системою каталогу, примірників, видач, резервування, оцінок і відгуків художньої та наукової літератури. Цей функціонал у D1 не дублюється. Чинний канонічний опис: [архітектура інтеграції Librarika](docs/LIBRARIKA_INTEGRATION_ARCHITECTURE_UK.md).

## Поточний виробничий контур

D1 є операційним ядром власної системи. Історичні документи Phase 1 та Google Sheets збережені для аудиту й відновлення, але не визначають чинну межу відповідальності Librarika/D1. Нові імпорти завжди проходять попередній перегляд і звіряння; чинний Site або базу не можна створювати заново.

## Нова архітектура даних

### D1 — операційне ядро

Після cutover D1 є єдиним runtime-джерелом для щоденної роботи сайту:

- підручники та інші навчальні матеріали, CAT-ID, бібліографічні поля й повнотекстовий пошук;
- посилання на електронні книги та сторінки з інформацією;
- місця зберігання, фактичні залишки та агреговану наявність;
- надходження й журнал руху примірників;
- користувачів і вчителів;
- видачі вчителям та повернення;
- ідемпотентні команди, версії записів і аудит змін;
- метадані чинних обкладинок.

Пошук і фільтри виконуються сервером. Список матеріалів завантажується сторінками, а важкі деталі — посилання й розміщення — лише після відкриття картки.

### Google Sheets — джерело міграції й архіву

Google Sheets більше не проєктується як primary runtime-база нового сайту. Під час Phase 1 вона потрібна для:

- канонічного експорту перед міграцією;
- reconciliation кількості матеріалів, посилань, користувачів, місць і залишків;
- збереження історичної копії на час контрольованого переходу;
- аварійного порівняння після cutover.

Формульні аркуші, тематичні каталоги, «Баланс» і старий аркуш «Ревізія» не переносяться як окремі runtime-таблиці. Потрібні представлення обчислюються з нормалізованих даних D1.

Після підтвердженого cutover таблицю слід перевести в режим архіву/лише читання. Не можна одночасно вести один фонд у D1 і Google Sheets як у двох незалежних головних базах.

## Щоденна робота бібліотекаря

Новий кабінет виконує основні операції напряму в D1, без проміжних чернеток Google Sheets:

- швидкий пошук за назвою, автором, ISBN або CAT-ID з підказками назв, фото, автора й року;
- вибір рубрики зі списку, включно з пунктом «Усі», та фільтри за класом, предметом, типом і наявністю;
- детальна картка з роком, фото, усіма службовими посиланнями й розміщеннями;
- створення матеріалу з автоматичним CAT-ID;
- додавання або заміна фотографії обкладинки без Google Sheets/GitHub bridge;
- пряме редагування картки та її посилань із перевіркою версії;
- безпечне видалення матеріалу з каталогу: CAT-ID, обкладинка й історія руху зберігаються, а матеріал із залишком або неповерненою видачею видалити не можна;
- початкове надходження разом зі створенням матеріалу;
- окреме надходження нових примірників;
- дія «Встановити фактичну кількість» замість окремого щоденного режиму «Ревізія»;
- видача вчителю з вибором за прізвищем;
- пакетна видача кількох назв і потрібної кількості примірників активному класу з відповідальним учителем;
- часткове або повне повернення з переліку відкритих видач учителям і класам.

Клас із неповерненою пакетною видачею не можна закрити або перевести на новий навчальний рік: спочатку потрібно прийняти всі примірники. Це не дає загубити заборгованість під час річного переходу.

Кожна операція запису має унікальний `requestId`, перевіряє очікувану версію або залишок і зберігає аудит. Повтор із тим самим `requestId` не повинен дублювати рух.

Legacy-код службових чернеток і Sheets gateway поки не видаляється: він потрібен для безпечного відкату та ще не перенесених адміністративних сценаріїв. Але він не є основним щоденним workflow Phase 1.

## Обкладинки

Чинні постійні URL обкладинок імпортуються як assets і продовжують показуватися в каталозі та кабінеті. Самі байти зображень міграційний loader не копіює.

Пряме додавання або заміна фото в новому D1-кабінеті реалізоване. Браузер готує компактний JPEG, сервер повторно перевіряє файл, постійні байти зберігаються в R2 під content-addressed ключем, а D1 зберігає версію, аудит та ідемпотентний результат команди.

Автоматичний пошук або додавання обкладинки за ISBN чи URL ще не реалізовані. Імпортовані зовнішні URL продовжують використовуватися як зовнішні джерела: loader не переносить їхні байти до R2. До окремого staging/cutover старий перевірений cover workflow не видаляється, а production-поведінка не вважається зміненою.

## Публічний каталог

Публічний API повертає лише дозволені поля. Приватні примітки, непублічні посилання, службові місця та персональні дані вчителів не повинні потрапляти до відповіді.

Каталог підтримує:

- курсорну пагінацію;
- пошук і серверні фільтри;
- сортування за назвою або новизною CAT-ID;
- рік видання й мініатюру в результатах;
- загальну, доступну й видану кількість;
- детальну картку з публічними посиланнями та дозволеними розміщеннями.

Чинна публічна адреса старої статичної версії: [https://nazarijshvetz1.github.io/library-site/](https://nazarijshvetz1.github.io/library-site/). Вона не є доказом, що D1 Phase 1 уже введено в production.

## Безпека запису

Захищені API повторно перевіряють автентифікацію, роль бібліотекаря, same-origin запит і серверний прапорець запису. Інтерфейс не може сам увімкнути production-запис.

Обов’язкові правила:

- `LIBRARIAN_WRITES_ENABLED=false` у production до окремого рішення про cutover;
- реальні email, токени, секрети й експорти не додаються до Git;
- `.migration-private/` не комітиться;
- кожний staging-імпорт має reconciliation-звіт;
- конфлікт первинного або унікального ключа зупиняє імпорт, а не перезаписує рядок;
- production D1 не підключається до локального CLI-loader;
- перед cutover потрібні резервні копії Sheets і D1 та перевірена процедура відкату.

`LIBRARIAN_WRITE_MODE`, `SPREADSHEET_ID`, `SHEETS_GATEWAY_URL` і HMAC-секрети стосуються legacy Sheets-контуру. Вони не роблять D1-запис безпечним і не замінюють staging/E2E-перевірку.

## Прив’язки Sites

У `.openai/hosting.json` зберігаються лише логічні binding-и:

- D1: `DB`;
- R2: `COVER_UPLOADS`.

Секретні runtime-значення зберігаються в налаштуваннях середовища, а не в репозиторії. Для захищеного кабінету потрібні щонайменше список дозволених користувачів і `LIBRARIAN_WRITES_ENABLED=false` до cutover.

## Локальна перевірка

Потрібен Node.js 22.18 або новіший.

```powershell
npm run build
npm run test:sites
```

Повний набір перевірок:

```powershell
npm test
```

Ключові Phase 1 тести охоплюють:

- D1 schema й міграції;
- імпортер та локальний loader;
- публічний і бібліотекарський read API;
- пряме створення й редагування матеріалу;
- надходження, фактичний підрахунок, видачу й повернення;
- конфлікти версій, залишків та повторні `requestId`;
- новий кабінет без окремого пункту «Ревізія».

Успішні локальні тести не дають дозволу на production rollout. Остаточний критерій — staging-імпорт реального експорту, reconciliation без невирішених конфліктів і E2E-перевірка всіх прямих операцій.
